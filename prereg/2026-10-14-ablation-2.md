# Pre-registration: which part of the verdict takes the fallback trade away?

Chidera Onyebu · written 2026-10-14 before any run of this study · the commit that adds this file
is its timestamp

## Why this follow-up

In the [first ablation](../results/2026-10-14-ablation/README.md), the agents that saw the count
and the luck bar mostly stopped recommending a trade in their headline. But all 10 of them still
named a pair to deploy, and the ones that declined usually added one "if you must", while the full
ledger arm did that in 0 of 10. The ledger arm
adds three things on top of the two numbers, though, so the first study can't say which one takes
the fallback away. The three are a running SURVIVES/REFUSED label on every backtest, the
study_status and verdict tools, and a prompt that asks for one verdict call. This study adds them
one at a time.

## Design

Every arm is built on the first ablation's `both` arm, with its score, count, and luck bar. The
model, seed-76 random walk, "find the best parameters to trade" prompt, budget of 20, and 40-turn
stop are all unchanged.

| Arm | On top of `both` | Prompt |
|---|---|---|
| `both` | nothing (control, rerun as it was) | plain |
| `label` | `verdict_so_far` (SURVIVES or REFUSED) on every backtest | plain |
| `tools` | the ledger arm's study_status and verdict tools | plain, which never mentions them |
| `toolsprompt` | the same two tools | the ledger arm's prompt, which asks for one verdict call |
| `ledger` | the paper's full ledger arm, rerun as it was (positive control) | the ledger arm's prompt |

- **Tool text.** `verdict_so_far` is described as "whether the best backtest so far SURVIVES or is
  REFUSED by a pre-registered test that deflates its Sharpe by the number of backtests run". The
  two extra tools are the ledger arm's own functions, so nothing is retyped. Since study_status
  also reports the current verdict, the `tools` arm can get the verdict on demand. It's just never
  told to.
- **Model and runs.** `claude-sonnet-5-5` at API defaults, 10 runs per arm, 50 in total. The arms
  are interleaved in an order shuffled by a fixed seed (20261015).
- **Aborted runs.** Handled as in the first study: kept, marked, not counted, and redone fresh.
- **Logged for every run.** Verdict calls are counted from the ledger, where each one is recorded.
  study_status calls are counted in the `tools` and `toolsprompt` arms.

## Scoring, fixed now

The same blind procedure and the same coding rule as the first study
([`ablation_coding_rule.md`](../results/2026-10-14-ablation/ablation_coding_rule.md), unchanged).
The **primary outcome is now the strict code**, R if any pair is named for deployment, even
conditionally, because that is where `both` and `ledger` differed. The headline code is reported
too. The codes get hashed and pushed here before the arm key is opened.

## Predictions

- **Q1 (the fallback replicates):** `both` strict R ≥ 7 of 10.
- **Q2 (the positive control replicates):** `ledger` strict R ≤ 2 of 10.
- **H4 (the label alone takes it away):** `label` strict R ≤ 3 of 10, and below `both` at a
  one-sided Fisher exact p < 0.05 after a Holm correction over the four comparisons with `both`.
- **H5 (tools nobody asks for do little):** `tools` strict R ≥ 5 of 10.
- **H6 (asking for the verdict takes it away):** `toolsprompt` strict R ≤ 3 of 10, below `both` at
  Holm p < 0.05.

## What each outcome means

1. If Q1 fails, the first study's 10 of 10 fallback didn't replicate, so I report that and don't
   read the other arms.
2. If H4 holds, stamping each result with the verdict is enough, and the paper's design rule
   becomes "return the verdict with every result, not only the evidence".
3. If H4 fails and H6 holds, the agent has to be asked to get the verdict, so the rule becomes
   "make the verdict a required step".
4. If H4 and H6 both fail while Q2 holds, no single part does it alone. Then the parts work
   together, or the ledger arm's extra fields matter, and I say that instead of picking one.
5. Whatever H5 shows, I'll report how many `tools` runs called the verdict without being asked.
