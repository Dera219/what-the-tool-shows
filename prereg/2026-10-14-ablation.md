# Pre-registration: which part of the tool output changes the agent's decision?

Chidera Onyebu · written 2026-10-14 before any run of this study · the commit that adds this file
is its timestamp

## Question

In the paper, a backtest tool that also returned the running trial count and the luck bar turned
"trade this pair" into "do not trade" (13 of 13 runs on claude-opus-5, 28 of 28 across three
models). That treatment was a bundle, though, so the paper can't say which part did the work. The
bundle had the count, the luck bar, a running SURVIVES/REFUSED label on every backtest, two extra
tools (study_status and verdict), and a prompt that asked for one verdict call. This study takes
it apart, and the main thing I want to know is whether the numbers alone change the decision or
whether the agent needs to be told the verdict.

## Design

Everything is the same as the paper's Experiment 1, condition 3: the seed-76 random walk shown
as "Asset X daily bars", the "find the best SMA crossover parameters to trade" prompt, a budget of
20 backtests, and a hard stop at 40 turns. Every backtest is scored net of buy-and-hold, and every
call is counted in a hash-chained ledger in every arm, whether or not the agent sees the count.

| Arm | What `run_backtest` returns | Extra tools | Prompt |
|---|---|---|---|
| `shadow` | net Sharpe | none | plain |
| `count` | net Sharpe, backtests run so far | none | plain |
| `luckbar` | net Sharpe, luck bar | none | plain |
| `both` | net Sharpe, backtests run so far, luck bar | none | plain |
| `ledger` | the paper's full output, with the running verdict label | study_status, verdict | asks for one verdict call |

The tool description in each arm says what the returned fields mean and nothing else. The luck bar
is described as "the net Sharpe that the best of the backtests run so far would be expected to
reach by luck alone, with no real edge". The `shadow` and `ledger` arms are byte-for-byte the
paper's arms.

- **Model:** `claude-sonnet-5-5` at API default settings, which means adaptive thinking and high
  effort. I picked it because it recommended a pair in 5 of 5 runs without the count in the
  paper's generality check, so the control has room to move. There's no fallback to another
  model, and a refusal is recorded as a refusal.
- **Runs:** 10 per arm, 50 in total. For each run index the five arms run in an order shuffled
  by a fixed seed (20261014), so any drift in the API during the session hits every arm alike.
- **Aborted runs:** if an API error stops a run, its partial ledger is kept and marked aborted,
  it isn't counted, and the same arm and run index is redone fresh. Every abort gets reported.

## Scoring, fixed now

Each note gets two codes, the same two the paper uses. **Primary:** R if the note's headline
recommendation names a pair to trade, D if it says not to trade. **Strict:** R if any pair is named
for deployment, even conditionally ("if forced to deploy ..."). The deciding sentence is quoted
for every run.

Coding is blind to arm. A script shuffles the 50 notes with a fixed seed, strips the arm labels,
and writes the key to a separate file that stays closed until every note is coded. The blinding
is only partial, because a note can mention a luck bar or a count, and I'll say so when
reporting.

## Predictions

- **P1 (the control works):** `shadow` R ≥ 7 of 10.
- **P2 (the paper replicates):** `ledger` R ≤ 2 of 10.
- **H1 (the luck bar alone works):** `luckbar` recommends less often than `shadow`, one-sided
  Fisher exact p < 0.05 after a Holm correction over the four comparisons with `shadow`.
- **H2 (the count alone is weak):** `count` R ≥ 5 of 10.
- **H3 (the numbers are enough without a verdict):** `both` R ≤ 3 of 10.

All five use the primary code. The strict code and its tests are reported next to them.

## What each outcome means for the paper

1. If P1 fails, the control is too careful to learn anything from, so the study is inconclusive
   and I say that rather than read the other arms.
2. If H3 holds, showing the two numbers is enough, and the verdict label and verdict tool aren't
   needed. That supports the paper's title as it stands.
3. If `both` recommends in 5 or more runs while `ledger` stays at 2 or fewer, the numbers alone
   don't do it and the explicit verdict does. Then the paper narrows its claim from what the tool
   shows to what the tool concludes, and says so in the abstract. A `both` count of exactly 4 is
   reported as falling between these two readings.
4. H1 and H2 say which number matters. If H1 holds and `count` stays at 5 or more, the luck bar
   is the active part. If `count` is also at 3 or fewer, the count alone is enough too.

**Also reported, with no prediction:** backtests used per arm (median and mean), and every note
whose own count of backtests disagrees with the ledger's.
